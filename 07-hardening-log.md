Regenerating the Prisma client there would break that server the next time it restarts. This worktree has its own `node_modules`, so it cannot.

Each one is tested from zero in a throwaway schema (`scratch_e2e`) first, then applied to the live database with `prisma migrate deploy`. Every migration so far only adds columns, tables or enum values, so the running dev server on the old code is unaffected. They are listed under "Migrations applied".
- **Unit tests never call a model.** Only the opt-in script in `scripts/eval/` does.
- Commits are small, and each passes `tsc`, `eslint` and the tests.

## Problems found while building

Each entry: what was wrong, why it matters, what was done, and whether it needs the owner.

### Phase 2

1. **The manual rubric editor lost data on every save.** It rebuilt the version from scratch and dropped the expected answer, the partial-credit guidance and the structured expectation. That silently changed how a question was routed and marked. It also dropped each approach's steps and which approach was primary. **Fixed:** every save is now a new version that carries every field forward and merges the editor's changes in; covered by tests. No decision needed.
2. **Every existing rubric on the live database is now "waiting for approval".** The migration deliberately gives them no approval, because backfilling one would claim a teacher approved something they did not. Effect: for an assessment that is already published, any *new* student submission is parked for the teacher ("scheme not approved") until a teacher approves its schemes (one "Approve all" click). The 9 existing submissions are unaffected. **Needs the owner:** keep it this way, or approve the existing schemes on behalf of the teacher.
3. **My own test bug.** `questions.map(questionRow)` passed the array index as the new `approved` argument, so the first question looked unapproved and ten submission tests failed. The code was right; the test helper was wrong. Fixed.
4. **A wrong test, mine.** A "correct answer, no working, full marks" test marked the final-answer criterion "no" while saying the answer was correct. Fixed the test.
5. **`tsc` in a fresh worktree reports `LayoutProps` not found** in `src/app/layout.tsx`. That type is generated by Next.js when it runs, so it is missing until `next dev` or `next build` has run once. Not a code problem; ignored in the checks.
6. **A scheme edit cannot be partially applied.** If a teacher's marks do not add up to the question, the save is refused with the reason, rather than the system adjusting their marks. This is deliberate (never silently change a teacher's marks), but it is stricter than the old editor, which accepted any total.

## Defaults chosen where the plan said "ask the owner"

The owner asked for all phases to be finished without stopping, so a conservative default was picked for each open question. **Each one needs a yes or a change at review.**

| Question | Default chosen | Why |
| --- | --- | --- |
| School-wide follow-through rule (Phase 2) | **Allowed** (`ALLOWED`) | The spec's own example is "follow-through allowed in maths". Settable per question on the scheme screen. |
| What a correct answer with no working earns (D6) | **Final-answer marks only**, and flagged | Straight from D6. Settable per question. |
| Default unit mark when the scheme is silent | **0.5 mark, only for questions worth 2 or more marks** that have a unit | A 1-mark question cannot be split sensibly. The generator adds a UNIT criterion on that rule; the teacher can change it. |

| A scheme that changes after a mark was accepted | **The mark is not changed; the teacher gets a "scheme changed" flag** | D13: never overwrite a confirmed mark. The flag does not compute "the draft would now be X" (see deviations). |

## Deviations from the plan

- **Unit handling keeps the older cautious rule for keys that have no unit.** The plan said to remove the "power-of-ten difference with a unit written makes no claim" rule. That rule now applies only to a rubric written before units were kept (the 9 live submissions' rubrics). A rubric generated from now on stores its unit and gets real conversion.
- **"Draft" is a rubric version status; the assessment status `RUBRIC_REVIEW` is not used.** An unapproved version has status `DRAFT`, no `approvedAt`, and is still the rubric's active version, so every existing reader keeps working. Approval sets `approvedAt`, `approvedById` and status `ACTIVE`. The plan's "MarkEvent-style record of who approved and when" is `approvedById` and `approvedAt` on the version itself, because a `MarkEvent` needs a student answer.
- **The "scheme changed" flag does not show the new draft mark** (the plan's "draft is now X (was Y)"). Computing it needs a marking run that is not saved. For now the teacher is told the scheme changed and decides.
- **The rubric's unit is stored as `unit` on the expected answer**, not as a separate `{ value, unit }` object.
